# PadTAS 設計書

## 1. 目的

実コントローラーの操作を「超繊細な操作でも再現できる精度」で記録し、
複数の記録を続きとして積み重ね (セグメント方式)、仮想コントローラーから
正確に再生する Windows アプリ。いわゆる TAS 支援ツールの入力記録/再生部分に特化する。

前提の線引き: 本アプリは「入力」の記録と再生を行う。
ゲーム本体のセーブステート (巻き戻し) はゲーム/エミュレータ側の機能であり、
本アプリからはホットキー送信による連携のみ行う (§6)。

## 2. 全体構成

```
実コントローラー
  │ XInput (生値)
  ▼
RecorderService ── 専用スレッド / QPC タイムスタンプ ──► RecorderEngine (Core)
                                                              │ 変化フレームのみ
                                                              ▼
プロジェクトフォルダ ── project.json (セグメント一覧)
                        └ seg-001.padtas, seg-002.padtas, ...
                                                              │ MergeAll() で連結
                                                              ▼
PlaybackService ── 絶対期限スケジューリング ──► IVirtualGamepad
                                                    └ ViGEmGamepad (ViGEmBus 仮想 Xbox 360)
                                                              ▼
                                                          ゲーム
更新: Velopack ── GitHub Releases を確認 → 差分DL → 再起動して適用
```

Core (OS 非依存) と App (Windows 固有: XInput / ViGEm / WPF) を分離し、
精度とデータ整合に関わる部分は Core に寄せて単体テスト可能にしている。

## 3. 精度設計 (最重要)

### 3.1 記録

| 項目 | 方式 | 理由 |
|---|---|---|
| ポーリング | 専用スレッド、250/500/1000 (既定) /2000Hz 選択可 | UI スレッドの描画に引きずられない |
| ポーリング周期の刻み | QPC ベース。残り >2ms は Sleep(1)、最後はスピン待機 | Thread.Sleep の既定粒度 (約15.6ms) では 60fps 内の精度も出ない |
| スレッド優先度 | Highest | 他アプリの負荷でサンプリングが飛ぶのを防ぐ |
| タイムスタンプ | QueryPerformanceCounter (Stopwatch)、分解能 約100ns、記録開始からの相対 tick | 壁時計は時刻補正で飛ぶため使わない |
| 保存する値 | ボタン 16bit、スティック int16 x4、トリガー byte x2、すべて生値 | デッドゾーン/平滑化/量子化は「情報を捨てる」ので記録時は禁止 |
| 保存する瞬間 | 状態が変化したときだけ (既定 epsilon=0、1 LSB 変化でも記録) | 無変化サンプルは再生に無意味。長時間でもファイルが小さい |
| ファイル内時刻 | 前フレームからの差分を 7bit 可変長で保存 | 精度を落とさず圧縮する |

### 3.1.1 同時入力の扱い

記録は「ボタンごとのイベント」ではなく「その瞬間の全状態のスナップショット」で
行うため、同時押しは構造的に欠けない。複数ボタン + 両スティック + 両トリガーが
同じサンプルで変化しても、1 フレームに全て入る。時間差で押された場合も
"押されている状態の合成" (例: A を保持したまま B を追加 → A|B) が残る。
再生側も ViGEm の自動送信を切り、全入力をセットしてから 1 レポートで送るため、
同時押しが複数のレポートに割れて届くことはない。
この性質は Core テスト (同時入力の 1 フレーム性、保存/読込、セグメント連結) で保証する。

### 3.2 再生

- 各フレームの送信期限 = 再生開始 QPC + フレーム相対 tick (**絶対期限方式**)。
  相対 Sleep の繰り返しは誤差が累積するので使わない。
- 期限直前は記録と同じくスピン待機で詰める。
- 最終フレーム後も記録の Duration まで状態を保持してからニュートラルに戻す
  (「最後の入力が何秒続いたか」も再現の一部)。

### 3.3 正直な限界 (設計で越えられないもの)

1. **コントローラー自体のポーリングレート**: 純正 Xbox コントローラーは約125Hz。
   アプリが 1000Hz で覗いても、新しい値は 8ms ごとにしか来ない。
   1000Hz 対応の有線コントローラーを使うとその分細かく取れる。
2. **ゲーム側の入力サンプリング**: 多くのゲームは描画フレーム (60fps 等) ごとに
   入力を読む。その場合、フレーム内の入力変化はゲームには見えない。
   つまり実効再現粒度は「ゲームの fps」が上限。本アプリはその上限まで
   誤差なく届けることが目標で、それ以上は原理的に不可能。
3. **Windows はリアルタイム OS ではない**: スピン待機 + 高優先度で
   実用上サブミリ秒級に抑えるが、厳密な保証はない。録画ソフト等の
   重い常駐は再生中のジッタ要因になる。

## 4. データ形式 (.padtas)

`docs` ではなく実装が正: `src/PadTas.Core/PadTasFile.cs` のコメントを参照。
要点: マジック `PADTAS` + 形式バージョン (uint16) + JSON ヘッダー
(コントローラー名、ポーリングレート、QPC 周波数、作成日時、長さ) +
フレーム列 (差分時刻 + 状態 12 バイト)。

QPC 周波数をヘッダーに持つため、別 PC で記録したファイルも秒換算できる。

## 5. セグメント方式 (続きからレコード)

- プロジェクト = セグメントの順序付きリスト (`project.json`)。
- 「記録開始 → 停止」で 1 セグメントが末尾に追加される。これが続き記録。
- 再生は `MergeAll()` で全セグメントを 1 本化する。境界では前セグメントの
  Duration 分だけオフセットし、次セグメント先頭フレームを境界時刻に置くため、
  境界で入力が途切れたり重なったりしない。
- セグメントは個別ファイルなので、記録済み分はクラッシュに強い。
- 今後の拡張 (ROADMAP): 途中位置からの録り直し = その位置で分割し、
  後半を捨てずに「ブランチ」として残す TAS 式リレコード。

## 6. セーブステート連携 (設計のみ、未実装)

エミュレータ等のクイックセーブ/ロードと入力記録を同期させるための案:
セグメントに `LoadStateHotkey` (例: F1) を持たせ、再生開始時にそのキーを
送信してから入力再生を始める。記録開始時も同様にセーブ側ホットキーを叩ける。
対象ゲームが固定される機能なので、実装は実利用タイトルが決まってから行う。

## 7. 再生出力

- 標準: ViGEmBus (仮想 Xbox 360 / DS4)。最終版 1.22.0 は署名済みで
  Windows 10/11 動作。ただし 2023 年に開発終了・アーカイブ済み。
- そのため出力は `IVirtualGamepad` インターフェース越しにし、
  将来の後継ドライバ (Virtual HID Driver 等) へ差し替え可能にしている。
- 実コントローラーと仮想コントローラーが同時にゲームに見えると
  二重入力になる場合がある。使う側で実機の接続を切るか、
  HidHide 等で実機を隠す運用を想定 (案内を UI に追加予定)。

## 8. 自動更新 (Velopack + GitHub Releases)

- 配布物は Velopack の Setup.exe。インストール先は `%LocalAppData%` (管理者不要)。
- アプリは起動時に GitHub Releases を確認し、新版があれば通知。
  「アップデート確認」ボタンから手動確認も可能。
- 更新は差分 (delta) パッケージ優先で小さい。再起動して自動適用される。
- バージョンの正は `PadTas.App.csproj` の `<Version>` と Git タグ `vX.Y.Z`。
  タグ push で `.github/workflows/release.yml` がビルド→パッケージ→Release 公開まで行う。
- 前提設定: `UpdateService.GitHubRepoUrl` を実リポジトリ URL に書き換えること (1か所)。

## 9. GitHub 運用

- `main` = 常にビルド可能。作業はブランチ → PR → CI (ビルド + Core テスト)。
- リリースはタグ駆動 (手作業のアップロードをしない)。
- 記録ファイル (*.padtas / プロジェクトフォルダ) は個人のプレイ記録なので
  リポジトリには入れない (.gitignore 済み)。

## 10. テスト

`tests/PadTas.Core.Tests` (コンソール式テストランナー、終了コードで成否):
- 1 LSB のスティック変化が記録されること (ロスレス)
- 変化なしサンプルが捨てられること
- .padtas 保存/読込の完全一致
- 2 セグメント連結で境界時刻と合計時間が一致すること
- 再生期限が絶対時刻で計算されること
